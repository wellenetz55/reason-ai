# 画面2：ベレネッツ管理画面

使う人: `operator` のみ。

## 1. 全社一覧

- 列: 会社名／状態／現在地（塗り・列）／次のセッション日／停滞日数／未回収宿題数／姿勢シグナル該当数／本業引き上げフラグ／開示要求回数
- 停滞7日以上は黄色。ワンクリックで「ひと押しメール」（テンプレ）
- フィルタ: 状態、今週セッションがある会社、フラグあり

## 2. 1社の詳細

### 2.1 進捗の位置
現在地と次のマイルストーン。塗りごとの承認状況（確定／保留／未レビューの行数）。顧客の作業ログ（いつ・どの行を・直した／承認／保留）。

### 2.2 停滞シグナル（外圧の材料）
- 宿題の回答状況と影響の自動算出（例: 「★★★3件が未回収 → ⑤⑥の要確認15件中9件が事実にならない」）
- 最終ログインからの経過日数、未レビュー行数
- 社内打ち合わせ未登録（W3〜5）

### 2.3 悩みの材料（セッションで話すこと）
- 保留が溜まった項目
- AI下書きと顧客の修正文の差分（並べて表示。最大の材料）
- 「ベレネッツに質問を残す」の未回答
- 根拠タグの分布（事実／要確認／仮説）＝適合診断3軸（素材・言語化・姿勢）の継続計測

### 2.4 姿勢シグナル
ログから機械的に拾う。単体では断定せず、複数該当でフラグ。点数ではなく事実の組み合わせで表示し、根拠の行番号にリンク。

| 系統 | サイン |
| --- | --- |
| 承認の仕方 | 10行以上を「直す」「保留」なしで連続承認／1行の滞在時間が文字数を読む時間を下回る／仮説タグの行を修正も保留もせず承認／行同士が矛盾したまま承認 |
| 修正の中身 | 全塗り通して修正文字数0／句読点・語尾だけの修正／「御社にしか書けない空欄」が埋まらないまま次へ／Q1が一度も触られていない |
| 時間の使い方 | セッション前日・当日に作業集中／1回のログインで全行処理／最終ログインからの空白日数 |
| 宿題 | 回答率、パス数／回答が「分からない」「ない」だけで誰に聞けば分かるかが無い |

表示例: 「3つが重なっています：仮説12件を全承認／修正ゼロ／宿題0件」→ セッションで聞く問いに変換して出す（「④の仮説、全部あるあるでしたか？」）。

### 2.5 赤入れ
- ⑤⑥⑦・⑧⑨の operator 版を入力。確認セッションまで顧客に非公開（セッション時に「開示」ボタン）
- 評価軸: 市場フィット6軸＋ブランド目的合致＋マグニチュード＋回天手法（1〜5ステップ）＋増減除付→順位。AIの仮採点を横に表示
  - 実装: `/admin/[companyId]/litmus`。組ごとに AI／御社／ベレネッツ の◎○△×を並べ、ベレネッツ列を入力（litmus_market scored_by=operator）。大きさ（magnitude_score ◎○△× と magnitude_text）、回天のステップ（kaiten_step 1〜5。名前は method_fixed_texts.kaiten_steps の5行）、増減除付（zougenjofu）、仮順位（litmus_market.rank）
  - ベレネッツ合計＝7軸＋大きさ。「合計点の高い順に仮順位を入れる」（保留候補＝2問とも「いいえ」と未採点は外す）→ 手で直す →「仮順位をお客様のシートに確定する」で sheet_rows.rank に写し、最上位を is_primary にする（同順位があると確定しない）
  - kaiten_step と rank は authenticated から列ごと SELECT 不可（SQL 0039）。operator 画面はサーバ側で読む。sheet_rows.rank / is_primary と litmus_market の kaiten_step・rank・magnitude_score は顧客ロールから書けない（トリガ）
- 競合優位性（どこ・どのように）
- 「封をする」ボタン（確認①／②／③）。封をブロックする条件の警告（⑤⑥に事実0件の行を1位にしようとしている等）。仮封のチェック
- 延長（最大4週）の付与、猶予・顧問の状態変更

### 2.6 開示要求ログ・本業引き上げ
- `disclosure_requests` の一覧（日時・質問文）。同一社3回以上で alert
- `questions_to_operator.kind=escalation` の一覧（売上・経営相談）。本業引き上げ候補フラグ

### 2.7 展開物のレビュー
- `deployments.status=awaiting_review` の一覧。生成物とブロック別の対応表（使った行・根拠タグ・**使った回天／脳科学手法**）。承認／差し戻し（理由）
- 顧問の月の生成数（10件）と猶予の残り（3件）

## 3. メソッド資産の管理（operator の中でも管理者のみ）

- 7面の問いテンプレ（周回別）、各塗りの固定文、回天×脳科学の手法表、システムプロンプト（バージョン管理）
- ここで投入した本文はサーバ側のみで使い、顧客向けAPIには出ない

## 適合診断の記録（/admin/[companyId]/intake）

operator だけが見る。顧客には出さない（`diagnosis_intakes`、customer ポリシー無し）。
- 対象：会社全体／事業部・ブランド／商品・サービス、対象の名前、運営会社・グループ内の関係。AIの下書き（STEP 0・STEP 1）は対象以外（親会社・他事業）の話を混ぜない
- URL：保存時に `company_documents`（kind=website）へ登録 → 顧客のSTEP 0に最初から入る
- 7問の答え（面談で聞いたまま）＋追加で聞いたこと。問いの文面は `method_fixed_texts`（diag_intro / diag_q1〜q7 / diag_guide）
- 録音の書き起こし（貼り付け or .txt/.md/.vtt/.pdf）。AIには先頭約4万字を渡す
- 判定メモ（適合／不適合／保留、3軸の一言）はAIに渡さない
- 契約前（diagnosed）の会社は、記録の判定が「適合」になるまで担当者の登録・招待（会社ページ／結果の公開と招待）ができない。顧客のメールアドレスは適合が固まってから入れる。契約後の会社には制限なし

### 面談メモ・資料（複数ファイル）
- 適合診断の記録ページの下で、ヒアリング中のメモや受け取った資料を複数まとめて登録できる（テキスト・PDF・Word(.docx)・画像、1ファイル25MB）。ドラッグでも可。
- 選ぶとすぐブラウザから保管場所（company-docs の `_intake/<会社ID>/`）へ直接送る。ページを読み直さないので、上で入力中の記録は消えない。
- 文字を取り出せたものは `diagnosis_intake_files.text_content` に入れ、書き起こしと同じくAI下書きの材料にする（書き起こしの半分の分量まで）。画像は保管のみ。お客様には出ない。
- 書き起こしの登録・外すは、記録と同じフォームで1回で保存する（入力中の内容が消えないように）。

### 顧客向けプレビュー（/admin/[companyId]/diagnosis/preview）
- 「結果を書く」の保存ボタンの下から開く。お客様の画面と同じ部品（`DiagnosisView`）で、保存済みの内容をそのまま表示。上部に「プレビュー」の帯。申込・日程のボタンは押せない。閲覧の記録は残さない。

### 適合診断を始める（記録ページ最下部の大きなボタン）
- 押すと、記録（7問・書き起こし・面談メモ）を保存したうえで AI（prompt key `diag_draft`、原則の分野「判定」「面談」）が、DB の判定手引き（`diag_guide`）に沿って判定案（適合／保留／不適合）と理由を出す。
- 判定案と理由は `diagnosis_intakes.verdict_note` の先頭に「【AI判定案：…】」として書く。判定（verdict）そのものは変えない。決めるのはベレネッツ。
- 「結果を書く」の空いている欄（一言・芽・ブレーキ・適合の理由）にだけ下書きを入れる。書いてある欄は上書きしない。公開済みなら下書きは入れない。
- 終わると「適合診断の結果を書く」へ移り、何を入れたかを通知で示す。

## 面談の記録（/admin/[companyId]/meetings/[meetingId]）
- 会社ページの各面談に「記録を書く」。面談した相手／聞いたこと（AIに渡す）／ベレネッツの気づき（渡さない）／書き起こし／メモ・資料（複数ファイル、`meeting_files`）。キックオフは加えて「当日の一言」「その場で作った組」。
- 「その場で作った組」は1行1組「提供価値｜体験価値」。「シートに入れる」で `sheet_rows` に created_by=operator・facet=functional・round=1 で追加（同じ提供価値は二重に入れない）。
- 「保存して、実施済にする」で held_at も立てる。
- AIへの渡し方：`loadMeetingContext()` が新しい面談から順に、一言・聞いたこと・組・メモファイルの文字・書き起こし抜粋をまとめ、会社プロフィールの下書きと `loadProfileContext`（STEP 1 の問い・下書き、なぜなら）に「適合診断より新しい情報として優先」で入る。
- SQL 0026。リセットの「やりとり」で面談ごと消える。

## データのリセット（/admin/[companyId]/reset）
- テストで入れた情報を消して、会社を最初の状態に戻すための機能。**スーパー管理者だけ**。会社ページの一番下から確認画面へ進む。
- 確認画面で、消す範囲（提供価値シート／STEP 0 の資料と会社プロフィール／宿題・質問・面談などのやりとり／適合診断の記録と結果／状態を「診断済み（契約前）」に戻す）と、それぞれの件数を見せる。最初はすべて選択。
- **会社名をそのまま入力したときだけ**実行ボタンが押せる（サーバー側でも同じ確認）。
- 実行前に、その会社の全データの控えを `backups` バケット `resets/<会社ID>/<日時>.json` に保存する。保存できなければ何も消さない。消した資料ファイルは `company-docs` の `_reset/<会社ID>/<日時>/` へ移す（お客様からは見えない）。
- 削除は SQL 0022 の `reset_company()` で1回のトランザクションで行う（途中で失敗したら何も消えない）。service role からだけ呼べる。
- 会社・会社名・担当者（サインインできる人）は消さない。
- 「sheet_rows は物理削除しない」原則の唯一の例外。通常の操作では引き続き status で管理する。

### ボールがベレネッツにある合図（step2_done）
- 顧客が「まとめて絞る」を終える（レビュー済みで未対応0）と `alerts(kind=escalation, payload.type=step2_done)` を1件だけ発行
- 発行と同時にオペレーター全員へメール（件名「◯◯ が「まとめて絞る」を終えました」）
- 全社一覧の最上部に「ベレネッツの番」バナー（会社名＋やること＋日付を列挙。急ぎアラートがある会社すべて）。行側も会社名の下に「ベレネッツの番」、アラート文は暖色太字、行は上に。文言「まとめて絞るが終わりました（確認セッション①の日程を決める）」
- 済みになる条件: 確認セッション①の面談を登録／状態を week1_2 以外に変更
- 「7日操作なし」は、その後7日以内に顧客操作があれば一覧に出さない（毎朝の自動処理で済みになるまでのずれを消す）
- 面談追加の種類プルダウン: 実施済みの種類は出さない。まだ登録のない次の面談（キックオフ→確認①→中間→確認②→確認③の順）を初期選択。顧問 月次・社内は常に末尾に
- 面談を実施済みにすると状態を自動で進める（operator 操作の一部）: キックオフ→week1_2／確認セッション①→week3_5／確認セッション②→week6_8（`ADVANCE_AFTER_MEETING`）。進んでいなければ会社ページ上部に「◯◯は実施済ですが状態が…のまま」の注意と1クリックで進めるボタン
